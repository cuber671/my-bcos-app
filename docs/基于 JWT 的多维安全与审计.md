在本区块链应用中，JWT 不仅仅是身份令牌，更是连接**前端交互、后端权限拦截与链上行为审计**的核心纽带。

## 1. 持久化登录机制 (Persistent Authentication)

系统采用无状态的 JWT 方案替代传统的 Session 模式，以支持高性能的并发处理。

* **双令牌策略** ：系统颁发 `Access Token`（短期，用于业务请求）与 `Refresh Token`（长期，用于自动续期）。
* **无缝续航** ：当 Access Token 过期时，前端利用 Refresh Token 获取新令牌，确保企业用户在处理复杂的票据业务时不会因登录中断导致数据丢失。
* **跨设备兼容** ：由于不依赖服务器内存存储 Session，支持集群部署，确保企业在多地办公时登录状态的一致性。

## 2. 细粒度角色权限认证 (RBAC & Functional Integrity)

JWT 载荷中封装的 `roleType` 是系统执行权限校验的唯一可信来源。

* **角色与接口对齐** ：后端拦截器解析 Token 中的角色字段。例如，只有 `roleType: 1`（核心企业）的 Token 才能通过“凭证签发”接口的验证；`roleType: 6`（金融机构）才能访问“放款审批”接口。
* **权限越级拦截** ：防止低权限角色通过直接调用 API 路径尝试执行高权限操作。
* **操作合法性校验** ：系统强制要求“当前操作内容”必须属于“当前登录实体”。

> **示例** ：供应商 A 尝试查询供应商 B 的资产。后端会比对 Token 中的 `entId` 与请求参数中的 `ownerId`。若不匹配，则立即判定为非法越权并记录安全预警。

## 3. 全链路无痛审计 (Seamless Operation Logging)

基于 JWT 的“身份注入”特性，系统实现了所有操作的精确归属，满足区块链业务的高审计要求。

* **操作一一对应** ：
* **业务层** ：每一条数据库更新记录（如修改企业资料、管理员工）都会自动从 JWT 中提取 `sub` (用户ID) 填入 `operator_id` 字段。
* **存证层** ：所有敏感行为（如生成邀请码、修改交易密码）在后端生成的日志中，都会携带 JWT 标识的唯一身份，确保“谁在什么时候做了什么”完全透明。
* **链上映射** ：当发起区块链交易时，JWT 的身份将与私钥签名后的 `blockchain_address` 进行逻辑绑定。在区块链浏览器中查看到的每一个 `txHash`，在后端系统里都能回溯到唯一的 JWT 登录记录。

## 4. 安全规范与约束

* **防篡改** ：所有 Token 均使用 **HS256** 或 RS256 算法签名，确保任何伪造角色的尝试都会导致验证失败。
* **敏感字段剥离** ：JWT 载荷严禁包含密码、加密私钥或未加密的社会信用代码等隐私信息，仅保留 ID、角色及账号名。
* **黑名单机制** ：针对异常操作或企业注销，系统会将特定的 `jti` (JWT ID) 存入 Redis 黑名单，强制其令牌失效。
