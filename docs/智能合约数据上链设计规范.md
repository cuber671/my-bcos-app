# 智能合约数据上链设计规范

## 一、设计原则

### 1.1 核心目标

智能合约的数据上链设计需要平衡三个目标：

| 目标             | 说明                                       |
| ---------------- | ------------------------------------------ |
| **防篡改** | 链上数据不可篡改，确保关键业务数据的真实性 |
| **防泄露** | 敏感隐私信息不上链明文，防止数据泄露       |
| **可核验** | 链下数据可通过哈希与链上比对，证明未被篡改 |

### 1.2 基本原则

```
链上存储成本高 → 只存"指纹"（哈希）
链下存储成本低 → 存完整数据
链上可验真伪 → 哈希比对
链下保隐私 → 敏感信息加密/哈希化
```

## 二、数据分类标准

### 2.1 三类数据对比

| 数据类别             | 处理方式            | 存储位置          | 示例               |
| -------------------- | ------------------- | ----------------- | ------------------ |
| **明文上链**   | 直接存储            | 区块链            | 资产ID、金额、数量 |
| **哈希化上链** | Hash(ID + Salt)     | 区块链            | 企业名称、身份证号 |
| **链下存证**   | 明文存储 + 哈希上链 | 数据库 + 链上哈希 | 详细合同、照片     |

### 2.2 判断流程

```
                    数据字段
                       │
                       ▼
              ┌────────────────┐
              │  是否需要公开  │
              │  检索/对账？  │
              └───────┬────────┘
                      │
           ┌────────┴────────┐
           │                 │
          是                否
           │                 │
           ▼                 ▼
     ┌──────────┐    ┌────────────────┐
     │ 明文上链 │    │ 是否涉及隐私？ │
     └──────────┘    └───────┬────────┘
                             │
                  ┌──────────┴──────────┐
                  │                     │
                 是                     否
                  │                     │
                  ▼                     ▼
          ┌────────────┐      ┌────────────────┐
          │  哈希化    │      │ 链下存证+哈希   │
          │  上链     │      │  上链          │
          └──────────┘      └────────────────┘
```

## 三、明文上链字段

### 3.1 明文上链定义

**明文上链**指原始数据以**明文形式**直接存储到区块链上，任何人都可以读取。

### 3.2 明文上链适用场景

| 场景               | 说明                     | 示例字段                      |
| ------------------ | ------------------------ | ----------------------------- |
| **公开检索** | 需要被外部系统查询       | receiptId, voucherId          |
| **业务对账** | 需要跨部门/跨机构核对    | weight, unit, amount          |
| **状态流转** | 业务状态变更需要链上记录 | status, balanceUnpaid         |
| **时间逻辑** | 需要基于时间判断业务规则 | dueDate, storageDate          |
| **金额计算** | 需要在链上执行数学运算   | initialAmount, financedAmount |

### 3.3 明文上链字段示例

```solidity
// ==================== 仓单模块 ====================
struct ReceiptCore {
    string receiptId;              // 仓单ID（公开检索）
    uint256 weight;               // 重量（业务对账）
    string unit;                  // 单位（吨/件/立方米）
    uint256 quantity;             // 数量（金额计算基础）
    ReceiptStatus status;         // 状态（状态流转）
    uint256 storageDate;          // 入库日期（时间逻辑）
    uint256 expiryDate;           // 过期日期（时间逻辑）
    bool frozen;                  // 冻结标志（状态控制）
}

// ==================== 物流模块 ====================
struct LogisticsCore {
    string voucherId;             // 物流凭证ID
    string targetWarehouseId;    // 目标仓库ID（公开检索）
    uint256 issueDate;           // 签发日期
    uint256 estimatedArrival;    // 预计到达时间
    LogisticsStatus status;      // 物流状态
}

// ==================== 应收款模块 ====================
struct ReceivableCore {
    string receivableId;          // 应收款ID
    uint256 initialAmount;       // 初始金额
    uint256 balanceUnpaid;      // 实时未还余额（每次还款更新）
    uint256 dueDate;             // 到期日期
    ReceivableStatus status;     // 状态
}
```

### 3.4 明文上链字段汇总表

| 模块   | 字段名            | 用途                     |
| ------ | ----------------- | ------------------------ |
| 仓单   | receiptId         | 唯一标识、公开检索       |
| 仓单   | weight            | 业务对账、金额计算       |
| 仓单   | unit              | 单位标准化               |
| 仓单   | status            | 状态流转控制             |
| 物流   | voucherId         | 唯一标识                 |
| 物流   | targetWarehouseId | 目标仓库检索             |
| 物流   | status            | 物流状态跟踪             |
| 应收款 | receivableId      | 唯一标识                 |
| 应收款 | initialAmount     | 金额计算基准             |
| 应收款 | balanceUnpaid     | 实时余额（每次还款更新） |
| 应收款 | dueDate           | 逾期判断依据             |

## 四、哈希化上链字段

### 4.1 哈希化定义

**哈希化上链**指将敏感信息通过哈希算法转换为不可逆的哈希值后存储到区块链上。

```
原始信息：企业名称 = "某某铝业有限公司"
盐值：     salt = "a7f3b2c1d9e8"
待哈希：   "某某铝业有限公司a7f3b2c1d9e8"
哈希值：   0x8f4e2b1a6c9d...（32字节）
```

### 4.2 哈希化适用场景

| 场景               | 说明                     | 示例字段                 |
| ------------------ | ------------------------ | ------------------------ |
| **隐私保护** | 不想让别人看到具体内容   | 企业名称、司机姓名       |
| **身份验证** | 证明"我是谁"但不透露信息 | ownerHash、warehouseHash |
| **配对验证** | 验证双方关系但不透露身份 | buyerSellerPairHash      |
| **凭证核对** | 验证证件号但不存储明文   | driverAuthHash           |

### 4.3 哈希化逻辑

#### 4.3.1 企业哈希

```solidity
// 用途：标识货主、仓库、企业身份
// 公式：Hash(EnterpriseID + RandomSalt)

struct ReceiptHashData {
    bytes32 ownerHash;       // 货主企业哈希
    bytes32 warehouseHash;   // 仓储企业哈希
}
```

#### 4.3.2 司机认证哈希

```solidity
// 用途：司机提货授权验证
// 公式：Hash(DriverID + LicenseNumber + RandomSalt)

struct LogisticsHashData {
    bytes32 driverAuthHash;  // 司机认证哈希
    bytes32 vehicleHash;     // 车辆信息哈希
}
```

#### 4.3.3 买卖对哈希

```solidity
// 用途：验证买卖关系但不透露具体企业
// 公式：Hash(BuyerID + SellerID + RandomSalt)

struct ReceivableHashData {
    bytes32 buyerSellerPairHash;  // 买卖对哈希
}
```

### 4.4 哈希化字段示例

```solidity
// ==================== 仓单模块 ====================
struct ReceiptHashData {
    string receiptId;
    bytes32 ownerHash;            // 货主企业哈希
    bytes32 warehouseHash;        // 仓储企业哈希
    bytes32 goodsDetailHash;      // 货物详情哈希（全摘要）
    bytes32 locationPhotoHash;    // 现场照片哈希（全摘要）
    bytes32 contractHash;         // 合同文件哈希（全摘要）
}

// ==================== 物流模块 ====================
struct LogisticsHashData {
    string voucherId;
    bytes32 driverAuthHash;       // 司机认证哈希
    bytes32 vehicleHash;         // 车辆信息哈希
    bytes32 gpsTrajectoryHash;   // GPS轨迹哈希（全摘要）
    bytes32 cargoDetailHash;     // 货物详情哈希（全摘要）
}

// ==================== 应收款模块 ====================
struct ReceivableHashData {
    string receivableId;
    bytes32 buyerSellerPairHash;  // 买卖对哈希
    bytes32 invoiceHash;         // 发票哈希（全摘要）
    bytes32 contractHash;         // 合同哈希（全摘要）
    bytes32 goodsDetailHash;      // 货物详情哈希（全摘要）
}
```

### 4.5 哈希化字段汇总表

| 模块   | 字段名              | 哈希公式                     | 用途         |
| ------ | ------------------- | ---------------------------- | ------------ |
| 仓单   | ownerHash           | Hash(货主ID + Salt)          | 货主身份验证 |
| 仓单   | warehouseHash       | Hash(仓库ID + Salt)          | 仓库身份验证 |
| 仓单   | goodsDetailHash     | Hash(IPFS_CID)               | 货物详情存证 |
| 仓单   | locationPhotoHash   | Hash(IPFS_CID)               | 现场照片存证 |
| 仓单   | contractHash        | Hash(IPFS_CID)               | 合同文件存证 |
| 物流   | driverAuthHash      | Hash(司机ID + 驾照号 + Salt) | 司机身份验证 |
| 物流   | vehicleHash         | Hash(车牌号 + Salt)          | 车辆信息验证 |
| 物流   | gpsTrajectoryHash   | Hash(IPFS_CID)               | GPS轨迹存证  |
| 应收款 | buyerSellerPairHash | Hash(买方ID + 卖方ID + Salt) | 买卖关系验证 |
| 应收款 | invoiceHash         | Hash(IPFS_CID)               | 发票存证     |
| 应收款 | contractHash        | Hash(IPFS_CID)               | 合同存证     |

## 五、全摘要存证

### 5.1 全摘要定义

**全摘要存证**指对大文件（图片、视频、PDF合同等）计算哈希值，将哈希值存储到链上，原始文件存储在链下（如IPFS）。

```
链上：照片哈希 = 0xabc123...
链下：IPFS存储原始照片
验证：链下读取照片 → 计算哈希 → 与链上比对
```

### 5.2 全摘要适用场景

| 场景               | 说明                 | 示例                 |
| ------------------ | -------------------- | -------------------- |
| **大文件**   | 数据量太大不适合上链 | 照片、视频、PDF      |
| **证据存证** | 需要证明文件未被篡改 | 现场照片、合同扫描件 |
| **轨迹数据** | GPS轨迹等时序数据    | 物流轨迹JSON         |
| **详细规格** | 复杂的技术参数       | 货物详细规格表       |

### 5.3 全摘要实现方式

```solidity
// 步骤1：Java后端上传文件到IPFS，得到CID
String ipfsCid = ipfsClient.upload(file);  // 例如：QmXyZ123...

// 步骤2：计算哈希（直接使用IPFS CID作为哈希）
String fileHash = "0x" + HexFormat.of().formatHex(ipfsCid.getBytes());

// 步骤3：将哈希上链
contract.issueReceipt({
    receiptId: "R001",
    weight: 100,
    ownerHash: "0x...",      // 企业哈希
    goodsDetailHash: fileHash  // IPFS哈希
});

// 步骤4：验证时，从IPFS下载文件，重新计算哈希并比对
```

## 七、栈溢出防护规则

### 7.1 问题背景

Solidity 0.8.x 使用 EVM EEP 内存模型，每个函数最多只能使用 **16 个局部变量**（包括函数参数和返回值）。超过这个限制会导致"Stack too shallow"编译错误。

### 7.2 防护规则

#### 规则一：使用 Struct 封装参数

```solidity
// ❌ 不推荐：参数过多，栈溢出风险
function createReceipt(
    string memory a,
    string memory b,
    string memory c,
    uint256 d,
    uint256 e,
    uint256 f,
    bytes32 g,
    bytes32 h,
    bytes32 i,
    address j,
    address k
) external {}

// ✅ 推荐：使用 Struct 封装
struct ReceiptInput {
    string receiptId;
    string ownerHash;
    string warehouseHash;
    uint256 weight;
    uint256 storageDate;
    bytes32 goodsDetailHash;
    address owner;
}

function createReceipt(ReceiptInput calldata input) external {}
```

#### 规则二：使用 Calldata 传参

```solidity
// ❌ 不推荐：memory 拷贝占用栈空间
function getReceipts(string[] memory ids)
    external view returns (ReceiptInfo[] memory) {}

// ✅ 推荐：calldata 不拷贝，节省栈空间
function getReceipts(string[] calldata ids)
    external view returns (ReceiptInfo[] memory) {}
```

#### 规则三：作用域隔离局部变量

```solidity
function complexOperation(...) external {
    // ❌ 不推荐：所有变量在一个作用域
    uint256 a = computeA();
    uint256 b = computeB();
    uint256 c = computeC();
    // ... 超过16个变量

    // ✅ 推荐：使用作用域隔离
    {
        uint256 a = computeA();
        uint256 b = computeB();
    }
    {
        uint256 c = computeC();
        uint256 d = computeD();
    }
}
```

#### 规则四：批量操作限制数量

```solidity
uint256 constant MAX_BATCH_SIZE = 50;

function getReceiptsBatch(string[] calldata receiptIds)
    external view returns (bool[] memory)
{
    // 限制批量大小，防止循环中栈溢出
    require(receiptIds.length <= MAX_BATCH_SIZE, "Batch size too large");

    bool[] memory results = new bool[](receiptIds.length);
    for (uint256 i = 0; i < receiptIds.length; i++) {
        results[i] = receiptExists(receiptIds[i]);
    }
    return results;
}
```

#### 规则五：分页查询

```solidity
function getReceiptsByPage(uint256 offset, uint256 limit)
    external view returns (ReceiptInfo[] memory)
{
    require(limit <= 100, "Limit too large");

    uint256 total = receiptCount;
    if (offset >= total) {
        return new ReceiptInfo[](0);
    }

    uint256 size = limit;
    if (offset + size > total) {
        size = total - offset;
    }

    ReceiptInfo[] memory results = new ReceiptInfo[](size);
    for (uint256 i = 0; i < size; i++) {
        results[i] = getReceiptInfo(receiptIds[offset + i]);
    }
    return results;
}
```

#### 规则六：拆分复杂函数

```solidity
// ❌ 不推荐：单个函数处理所有逻辑
function processEverything(Input input) external {
    // 验证
    validate(input);
    // 处理A
    processA(input);
    // 处理B
    processB(input);
    // 处理C
    processC(input);
}

// ✅ 推荐：拆分为多个函数
function processEverything(Input input) external {
    validate(input);
    processA(input);
}

function processA(Input input) internal {
    processB(input);
}

function processB(Input input) internal {
    processC(input);
}
```

### 7.3 栈溢出检查清单

```
□ 函数参数是否超过16个？
□ 是否使用了struct封装？
□ 是否使用了calldata？
□ 批量操作是否限制了数量？
□ 是否需要分页查询？
□ 循环中变量是否过多？
```

## 八、总结

### 8.1 上链决策总结

| 数据特征         | 推荐方式   | 示例                      |
| ---------------- | ---------- | ------------------------- |
| 需要公开检索     | 明文上链   | receiptId, amount         |
| 涉及金额计算     | 明文上链   | balanceUnpaid             |
| 业务状态流转     | 明文上链   | status                    |
| 时间逻辑判断     | 明文上链   | dueDate                   |
| 隐私信息（身份） | 哈希化上链 | ownerHash, driverAuthHash |
| 隐私信息（配对） | 哈希化上链 | buyerSellerPairHash       |
| 大文件数据       | 全摘要存证 | photoHash, contractHash   |
| 时序轨迹数据     | 全摘要存证 | gpsTrajectoryHash         |

### 8.2 设计流程

```

      ▼

      │
      ▼

      │
      ▼
5. 选择上链方式
      │
      ▼
6. 验证栈溢出风险
```

## 九、合约拆分原则

### 9.1 不必所有字段都上链

实体类中的字段不一定都需要在链上存储，需要根据业务需求和数据特性选择性地存储：

| 存储方式 | 适用场景 | 示例 |
|---------|---------|------|
| **链上存储** | 与核心业务逻辑、区块链共识相关的关键字段 | receiptId、weight、status、ownerHash |
| **链下存储** | 仅用于展示、统计的辅助字段 | 备注信息、创建人头像 |
| **完全链下** | 纯业务数据，不需要区块链背书 | 业务流程日志、内部管理数据 |

**设计原则**：链上只存储"必须要在区块链上共识的数据"，其他数据存于链下数据库。

### 9.2 合约拆分策略

当单个合约变得过于复杂时，可以拆分为多个合约：

| 拆分策略 | 说明 | 示例 |
|---------|------|------|
| **按功能拆分** | 将不同业务功能拆分为独立合约 | WarehouseReceipt + WarehouseReceiptCancel |
| **按数据拆分** | 将不同类型的数据拆分到不同合约 | ReceiptCore + ReceiptHistory |
| **按栈溢出拆分** | 将复杂函数拆分到独立合约 | MainContract + HelperContract |

**拆分优势**：
- 避免栈溢出问题
- 便于合约的升级和维护
- 提高代码的可读性和可测试性
- 每个合约可以独立部署和升级

**拆分示例**：

```solidity
// 拆分前：单个复杂合约
contract WarehouseReceiptFull {
    // 仓单核心功能
    function createReceipt(...) ...
    function transferReceipt(...) ...
    function splitReceipt(...) ...
    function mergeReceipts(...) ...

    // 取消功能
    function cancelReceipt(...) ...

    // 变更历史
    function recordHistory(...) ...
    function getHistory(...) ...
}

// 拆分后：多个独立合约
contract WarehouseReceiptCore {
    // 仅核心功能
    function createReceipt(...) ...
    function transferReceipt(...) ...
```
