
1. **遵循 RESTful 设计原则**
   * 动词严格映射 HTTP 方法：GET（查询）、POST（创建）、PUT（全量更新）、PATCH（部分更新）、DELETE（删除），禁止用 URL 携带动词（如 `/api/v1/deleteAsset` 需改为 `DELETE /api/v1/assets/{assetId}`）；
   * 名词使用资源复数形式（如 `/api/v1/assets` 而非 `/api/v1/asset`），嵌套资源通过层级表达（如 `/api/v1/assets/{assetId}/transactions` 表示某资产下的交易）；
   * 过滤 / 排序参数通过 Query 传递（如 `/api/v1/assets?status=active&sort=createTime&order=desc`），禁止写入路径。
2. **使用标准 HTTP 状态码**
   * 核心状态码及场景：
     * 200 OK（查询 / 更新成功）、201 Created（资源创建成功）、202 Accepted（异步请求接收成功）；
     * 400 Bad Request（参数格式错误）、401 Unauthorized（未认证）、403 Forbidden（无权限）、404 Not Found（资源不存在）、409 Conflict（资源冲突，如重复创建）、429 Too Many Requests（请求限流）；
     * 500 Internal Server Error（系统异常）、503 Service Unavailable（节点 / 服务不可用）；
   * 状态码与业务码解耦：HTTP 状态码仅反映「请求传输 / 处理状态」，业务逻辑结果由业务码 `code` 表达。
3. **响应格式统一**
   * 强制结构（JSON 格式）：
     json

     ```
     // 成功响应
     {
       "code": 0,          // 0=业务成功，非0=业务错误码
       "msg": "操作成功",  // 生产环境为用户友好提示，测试环境可包含调试信息
       "data": {}          // 无数据时返回 null，而非空字符串/空数组
     }
     // 失败响应
     {
       "code": 20002,
       "msg": "用户余额不足",
       "data": null
     }
     ```
4. **分页元数据**
   * 入参规范：`page`（默认 1，最小值 1）、`pageSize`（默认 10，最大值 100）；
   * 响应规范：分页元数据封装在 `pagination` 节点，示例：
     json

     ```
     {
       "code": 0,
       "msg": "查询成功",
       "data": {
         "list": [...],    // 数据列表
         "pagination": {
           "total": 100,   // 总数
           "page": 1,      // 当前页码
           "pageSize": 10, // 页长
           "pages": 10     // 总页数（total/pageSize 向上取整）
         }
       }
     }
     ```
5. **版本控制**
   * 版本号仅包含主版本（如 `/api/v1/`/`/api/v2/`），避免 `v1.1` 等细分版本；
   * 兼容策略：旧版本保留至少 3 个月，响应头添加 `Deprecated: true` 及替代接口路径；
   * 路由隔离：通过网关实现版本路由隔离，避免代码耦合。
6. **字段命名**
   * 强制统一为小驼峰（`camelCase`），与 Java 实体类 / 合约包装类完全一致；
   * 特殊字段规范：
     * 区块链地址：`address`（禁用 `addr`/`addressStr`）；
     * 交易哈希：`txHash`（禁用 `transactionHash`/`hash`）；
     * 时间字段：`createTime`/`updateTime`，格式为 UTC+8 的 ISO 8601 字符串（如 `2026-02-19T15:30:00+08:00`）；
   * 禁止拼音 / 中英文混合命名（如 `zichanId` → `assetId`）。

### 二、 错误处理规则（完善版）

1. **统一错误响应格式**
   * 继承基础响应结构，测试 / 预发环境可新增 `errorStack`，生产环境强制屏蔽：
     json

     ```
     // 测试环境错误响应
     {
       "code": 10001,
       "msg": "合约调用失败：Revert(error: 'insufficient allowance')",
       "data": null,
       "errorStack": "com.contract.CallException: ...（完整堆栈）"
     }
     ```
2. **业务码体系**
   * 分段管理（便于定位模块）：
     * 10000-19999：合约调用错误（10001 = 合约调用失败，10002 = 合约地址无效）；
     * 20000-29999：用户 / 权限错误（20001 = 用户不存在，20002 = 密码错误）；
     * 30000-39999：参数校验错误（30001 = 参数缺失，30002 = 参数格式非法）；
     * 40000-49999：系统 / 节点错误（40001 = 节点连接失败，40002 = 请求超时）；
   * 文档化要求：维护可检索的业务码字典，包含「码值、含义、触发场景、解决方案」。
3. **错误日志分级**
   * 分级及场景：
     * Debug：开发调试信息（如合约入参 / 出参），仅测试环境开启；
     * Info：正常业务日志（如交易提交成功）；
     * Warn：用户输入错误、非致命业务异常（如余额不足）；
     * Error：系统异常、合约 Revert、节点连接失败；
     * Fatal：核心服务不可用（如节点全量宕机），需触发告警；
   * 日志内容：必含 `traceId`（链路 ID）、`userId`、`txHash`、`timestamp`，敏感信息脱敏（如手机号 138****1234）。
4. **脱敏处理**
   * 禁止返回：数据库主键、服务器 / 节点内部 IP、私钥 / 助记词、数据库连接串；
   * 脱敏返回：手机号（前 3 后 4 隐藏）、身份证号（前 6 后 4 隐藏）、钱包地址（0x1234****abcd）；
   * 脱敏规则：全系统统一，避免前端 / 服务端脱敏不一致。

### 三、 安全规则（完善版）

1. **认证与授权**
   * 基础认证：所有接口默认 JWT 校验，JWT 包含 `userId`/`role`/`exp`（过期 2 小时），密钥每 3 个月轮换；
   * 二次校验（敏感操作）：发起链上交易、修改资产归属等操作需额外校验「用户签名」或「短信 / 邮箱验证码」；
   * 权限粒度：基于 RBAC 模型，细化至「接口 + 操作」（如 `assets:create`/`assets:delete`）；
   * 匿名接口：仅开放健康检查 `/api/v1/health` 等必要接口，且需限流。
2. **传输加密**
   * 基础要求：全量接口强制 HTTPS（TLS 1.2+），禁用 HTTP；
   * 敏感数据加密：
     * 私钥 / 助记词：前端 RSA 公钥加密后传输，服务端仅存密文，解密仅在内存执行；
     * 交易哈希 / 资产 ID：按需 AES-256 加密传输，密钥非硬编码。
3. **防注入与验证**
   * 参数校验：前端 + 服务端双重校验（如区块链地址需校验 42 位 hex 格式），服务端使用 Validator 框架强制校验；
   * 防 SQL 注入：使用预编译语句 / ORM 框架，禁止拼接 SQL；
   * 防合约攻击：调用前校验参数范围（如金额防溢出）、限制 gas 上限、合约地址白名单机制。
4. **限流与熔断**
   * 限流规则：按 IP / 用户 ID / 接口维度限流，查询接口单用户 10 QPS、写入接口单用户 2 QPS，触发后返回 429；
   * 熔断规则：节点调用失败率 > 50% 时触发熔断（30 秒），返回兜底响应，避免服务雪崩。

### 四、 性能与可靠性（完善版）

1. **接口幂等性**
   * 实现方案：写入类接口入参必传 `transactionId`（UUID），服务端通过「transactionId + userId」建立唯一索引，重复请求直接返回已处理结果；
   * 有效期：`transactionId` 有效期 24 小时，过期后允许重新提交。
2. **异步处理**
   * 响应流程：
     1. 前端发起写入请求，服务端校验后生成 `txHash`，立即返回 202 Accepted（含 `txHash`/`transactionId`）；
     2. 服务端异步调用合约，结果写入数据库 / 缓存；
     3. 前端通过 WebSocket（推荐）或轮询（`/api/v1/transactions/{txHash}/status`，间隔≥1 秒，最多 30 次）获取结果；
   * 任务管理：异步任务支持重试（最多 3 次，间隔 5 秒），使用分布式任务框架（如 XXL-Job）管理。
3. **超时控制**
   * 分级超时：接口整体 5 秒、合约调用 3 秒、数据库操作 1 秒；
   * 超时处理：立即中断请求，返回业务码 **40003**，记录 Error 日志；
   * 重试规则：查询接口最多 1 次重试，写入接口禁止重试（依赖幂等）。
